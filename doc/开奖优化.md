# 开奖优化方案：按当日真实订单自动推荐可选盈利/亏损方案

## 一、客户需求理解

客户反馈的核心问题不是“杀率公式算错”，而是开奖结果是离散的。

当前系统可以按当日投注自动计算一个开奖计划，但是在订单数量少、单笔金额大、投注集中时，后台输入一个目标杀率，例如 10% 或 20%，系统未必真的存在刚好接近该比例的开奖结果。原因是每一组 7 个开奖号码都会对应固定的派彩金额，平台利润只能落在若干个离散点上，不能像连续百分比一样任意调节。

例如：

- 今日投注总额：50000
- 某个可开方案需要派彩：47000
- 平台利润：3000
- 实际盈利率：3000 / 50000 = 6%

这种情况下，管理员想杀 10% 或 20%，但真实可开方案可能只有 6%、15.8%、35.9%、70% 等离散结果。如果系统为了追求 20% 而选通杀方案，就会偏离客户真实意图。客户想要的是：封盘后，后台自动把当天所有可选开奖方案的赔付和盈利点算出来，直接展示给管理员选择。

因此，本次优化目标应定义为：

封盘后，根据当日当前期号的真实订单，模拟多个可用开奖结果，输出每个方案的投注额、预计派彩、预计利润、预计盈利率/杀率。系统不只返回一个“最接近目标”的结果，而是一次性把本期可选的多种正盈利和负盈利方案都展示出来，例如 18%、30%、70%、100%，以及可控亏损方案。管理员最终从这些方案里人工选择一个，系统先锁定为本期人工计划；真正对外开奖和结算必须等到后台配置的开奖时间，也就是前端用户看到的同一个开奖时间。

## 二、客户已确认的口径

以下内容已根据客户本次回复确认，后续开发按这些口径执行。

1. 杀率/盈利率分母

   按当期当前期号的总投注额计算。

   ```text
   平台利润 = 总投注额 - 总派彩金额
   盈利率/杀率 = 平台利润 / 总投注额 * 100%
   ```

2. 负盈利口径

   负盈利也按当期当前期号的下注金额作为分母。

   ```text
   -5% = 平台亏损金额约为总投注额的 5%
   例如总投注 50000，-5% 表示预计亏损约 2500。
   ```

3. 目标杀率找不到时的展示方式

   客户不是只要一个最接近结果，而是希望后台把本期能实现的几种杀率都展示出来。例如本期只有 18%、30%、70%、100% 这些可选盈利点，就把这些方案都给到管理员。

   因此推荐结果应同时包含：

   - 最接近目标的方案
   - 低于目标的最近方案
   - 高于目标的最近方案
   - 其他代表性盈利档位，例如 30%、70%、100% 附近
   - 负盈利代表性档位，例如 -5%、-10%、-15%、-20% 附近

4. 正盈利和负盈利一次性生成

   进入开奖准备时，后台一次性生成本期的盈利方案和负盈利方案，管理员自己选择，不要只在点击某个负盈利按钮时才临时计算。

5. 负盈利必须人工选择

   负盈利方案只能作为人工可选方案展示，不能由自动任务默认选择。管理员选择负盈利方案时，必须二次确认并显示预计亏损金额。

6. 选择方案后的动作

   客户已明确：未到开奖时间可以选择方案，但不允许立即开奖结算。选择方案后只是确认本期杀率和开奖计划，系统应写入 `planned_result` 并与前端开奖时间同步，等到后台配置的开奖时间再正式公布 `result` 并结算。

7. 开奖时间标准

   后台开奖时间和前端用户看到的开奖时间必须一致。例如后台开奖时间是 8:33，前端客户开奖核对也必须是 8:33，以这个时间作为公布和结算标准。

8. 未选择正盈利方案时的处理

   如果本期有投注，并且有正盈利方案但管理员没有选择，系统不自动替管理员选择，等待人工处理。

9. 封盘前不展示方案

   客户已确认：封盘前不显示盈利/负盈利方案，也不做后台可见的方案预览。只有封盘后，当期订单固定后，系统才生成本期可选方案，并允许总管理员选择和锁定。

10. 无投注期次的处理

   客户已确认：如果封盘后本期没有任何投注，到开奖时间可以由系统自动随机开奖，不需要总管理员选择方案。因为没有投注就没有派彩和杀率风险，自动开奖后应继续创建下一期。

11. 期号自动延续

   客户关注：如果今天已经开到 180 期，后面一个星期后台都没有人工操作，系统是否会自动创建 181 期并继续往后开奖。按最新需求，系统应该支持无人值守延续：只要定时任务正常运行，无投注期次到开奖时间自动开奖，开奖完成后自动创建下一期，并按盘口配置时间继续进入开盘、封盘、开奖流程。

## 三、已确认的展示和权限细节

核心业务口径已经确认。以下展示和权限细节按客户最新回复执行。

1. “100%”或“通杀”是否作为普通可选方案展示？

   已确认：通杀 100% 展示在同一列表，例如本期可杀 10%、28%、30%、70%、100%。建议将利润率接近 100%、预计派彩为 0 的方案标记为“通杀/近似通杀”，并增加二次确认，避免误点。

2. 封盘前是否展示方案？

   已确认：封盘前不展示任何盈利/负盈利方案；封盘后再生成方案。因为封盘前订单还会变化，提前展示的盈利点不稳定，容易让后台误判。

3. 权限和日志细节

   已确认：负盈利、改选、撤销只允许总管理员操作。所有方案选择都写操作日志，负盈利方案额外写预计亏损金额和二次确认标识。

4. 改选和撤销时间

   已确认：正式开奖时间前都可以改选或撤销。例如 8:33 开奖，只要还没到 8:33、还没正式公布和结算，总管理员就可以改。

当前主要计算逻辑在：

```text
server/app/common/service/OptimizedBestPlanService.php
```

关键点：

- 构造函数会加载当前 `gid + qishu + plate_code` 的所有订单。
- `findBest7Numbers()` 会生成候选 7 码方案。
- `calculateCombinedProfit()` 会模拟某组号码下的总派彩。

这说明底层已经具备“计算每个方案赔付和盈利点”的基础。

### 2. 推荐接口层

当前主要逻辑在：


- `customDrawing()` 当前只校验封盘时间，之前已发现业务上应改成开奖时间到才允许立即开奖。

### 6. 选择推荐方案后锁定开奖计划

客户已确认未到开奖时间可选择方案，但不允许立即开奖结算。主流程建议新增一个更明确的方法，例如：

```php
public static function lockRecommendedSolution(
    int $gid,
    string $qishu,
    string $plateCode,
    array $numbers,
    int $year,
    int $operatorId,
    array $expected,
    bool $allowNegative = false
)
```

处理流程：

```text
1. 锁定 la_lottery_issue 当前期号。
2. 校验期号存在、未开奖、未结算。
3. 校验已封盘；未到 draw_time 也允许选择方案，但不允许结算。
4. 重新用当前订单模拟该组号码，重新计算预计派彩、预计利润、预计杀率。
5. 如果方案为负盈利，必须要求 allow_negative = 1，并记录二次确认。
6. 写入 la_lottery_issue.planned_result、planned_source、planned_operator_id、planned_at。
7. 不写入 la_lottery_issue.result。
8. 不调用结算逻辑，不更新用户余额和订单状态。
9. 保存选择目标率、实际杀率、预计派彩、预计利润，作为审计。
10. 等 draw_time 到达后，由 `draw:lottery` 使用 `planned_result` 写入 `result` 并结算。
```

返回结果：

```php
[
    'issue' => $qishu,
    'plate_code' => $plateCode,
    'planned_numbers' => $numbers,
    'target_rate' => 20.00,
    'expected_profit_rate' => 18.37,
    'total_bet_amount' => 50000.00,
    'expected_payout' => 40815.00,
```

## 九、风险点

1. 性能风险

   如果要求“枚举全部 7 码组合”，组合数量非常大。现有算法是候选搜索，适合推荐若干方案；如果客户要求完全穷举，需要独立做性能评估和缓存。

2. 负盈利风险

   负盈利必须只允许总管理员操作，并且必须有二次确认和操作日志。客户已确认负盈利必须人工选择，自动任务不能默认选负盈利。

3. 开奖时间同步风险

   客户已确认后台和前端必须使用同一个开奖时间。后台允许提前选择方案，但 `result` 公布和订单结算必须等 `draw_time/kjtime`，不能提前。

4. 开奖时间风险

   `customDrawing()` 和所有立即结算入口都必须校验 `draw_time`。封盘后只能锁定计划，不能对外开奖结算。

5. 历史数据一致性

   当前历史分析表和投注记录表不是同一张表，开奖后必须同步，否则仍可能出现“订单已结算但控盘历史未开奖”的显示问题。

## 十、当前确认结论话术

可以这样总结给客户：

```text
已确认：系统不要强行按固定 10%、20% 去开奖，因为开奖结果是有限的，不一定刚好存在 20% 的盈利点。封盘后系统应该根据当期真实订单，自动算出本期多组可选开奖方案，并显示每组的预计派彩、预计盈利/亏损、实际盈利率。比如本期能做到 18%、30%、70%、100%，就把这些方案都给到后台选择，不要因为找不到 20% 就直接变成通杀。

负盈利也按同一套逻辑一次性生成，比如 -5%、-10%、-15%、-20% 附近，系统展示预计亏多少，只有管理员人工确认后才能选择，不能自动选择负盈利。

后台未到开奖时间可以选择方案，但不允许立即开奖结算。选择后只锁定本期开奖结果计划，前端和后台都以同一个开奖时间为准，例如后台开奖时间 8:33，前端用户开奖核对也必须是 8:33。到这个时间后系统才公布开奖结果并结算。

如果没有选择正盈利方案，系统等待人工处理。
```

## 十一、结论

这个需求可以在现有代码基础上开发，不需要推翻现有开奖结算架构。底层已经能模拟不同 7 码组合的派彩和利润，主要改动集中在：

- 后端增加“按目标杀率推荐方案”的接口。
- 一次性生成正盈利和负盈利方案。
- 负盈利方案只允许管理员人工选择，自动任务不默认选择负盈利。
- 前端增加正盈利/负盈利按钮和推荐结果展示。
- 选择推荐方案后锁定 `planned_result`，到统一开奖时间再公布并结算。
- 保存选择方案的预计值，开奖后同步实际利润，保证历史记录一致。

## 十二、代码复查后的补充项

本次按现有代码再复查后，除了“杀率推荐算法”和“前端按钮”之外，还必须补以下几处，否则会和客户已确认的口径冲突。

### 1. 定时开奖任务不能再绕过人工选择

现有代码位置：

- `server/app/common/command/DrawLottery.php::planClosedIssues()`
- `server/app/common/command/DrawLottery.php::publishAndSettleDueIssues()`
- `server/app/common/model/lottery/LotteryIssue.php::getPendingPlanIssues()`
- `server/app/common/model/lottery/LotteryIssue.php::getPendingDrawIssues()`

当前逻辑：

- 封盘后、开奖前 2 分钟，`planClosedIssues()` 会自动计算并写入 `planned_result`。
- 如果计算失败，还可能走 `generateFallbackResult()` 随机号码。
- 到 `draw_time` 后，`publishAndSettleDueIssues()` 会按 `result -> planned_result -> fallback_random` 的优先级开奖结算。
- 也就是说，即使有投注的期次后台没有人工选择方案，系统仍可能自动开出一组号码并结算；这部分需要禁止。无投注期次则按客户最新确认允许自动随机开奖。

客户已确认：

- 选择正盈利方案后才锁定计划。
- 有投注期次没有选择正盈利方案，等待人工处理。
- 无投注期次到开奖时间允许系统自动随机开奖，并继续创建下一期。
- 负盈利必须人工选择。

因此开发时必须调整为：

1. 增加“人工控盘模式”判断，建议按彩种/盘口配置，例如 `manual_plan_required = 1`。
2. 在人工控盘模式下，`planClosedIssues()` 不自动写入 `planned_result`。
3. 在人工控盘模式下，到 `draw_time` 仍没有 `planned_result` 时，`publishAndSettleDueIssues()` 不能随机兜底开奖，也不能结算。
4. 未选择方案的期次应保持“待人工处理/待开奖计划”状态，并写日志或后台告警。
5. 如果后续要保留普通玩法的自动开奖，可通过配置区分：普通模式继续自动计划，控盘模式必须人工选择。
6. 封盘前不生成、不展示方案；封盘后才按当期订单一次性生成本期可选盈利和负盈利方案。

这是 P0 级改动。如果不改这里，即使推荐方案做出来，定时任务仍可能在后台没有选择时自动开奖，直接违背客户第 2 个确认点。

### 2. `executeDrawing()` 需要补封盘和方案快照校验

现有代码位置：

- `server/app/adminapi/controller/BestPlanController.php::executeDrawing()`
- `server/app/adminapi/logic/BestPlanLogic.php::executeDrawing()`
- `server/app/api/logic/BestPlanLogic.php::executeDrawing()`

当前逻辑：

- 已经改成写 `planned_result`，不直接写 `result`，不立即结算。
- 会拒绝已开奖、已结算、已有手动 `planned_result` 的期次。
- 但 API 逻辑层目前没有明确校验 `close_time`，如果接口被直接调用，可能在封盘前就锁定计划。
- 只接收 `best_numbers`，没有接收或保存本次选择对应的目标杀率、实际杀率、预计派彩、预计利润、是否负盈利等快照。

建议调整为：

1. 后端强制校验：只能在 `close_time <= now < draw_time` 的窗口内选择开奖计划，封盘前不允许预览锁定、不允许提交计划。
2. 后端收到号码后，必须重新按当期订单计算预计派彩、预计盈利、实际杀率，不能信任前端传来的金额。
3. 选择方案时保存完整快照：`target_rate`、`actual_profit_rate`、`expected_profit`、`expected_payout`、`total_bets`、`total_orders`、`is_negative_plan`、`selected_source`、`selected_operator_id`、`selected_at`。
4. 正盈利普通方案可直接确认；负盈利方案必须带 `allow_negative = 1`，并增加二次确认和操作日志。
5. 返回字段和前端文案应改为“开奖计划已锁定/预计派彩/预计盈利”，不能再叫“开奖成功”。

### 3. `customDrawing()` 仍是立即开奖结算入口，必须按开奖时间限制

现有代码位置：

- `server/app/api/logic/BestPlanLogic.php::customDrawing()`

- `vue/admin/apps/web-antd/src/views/control-panel/analysis/index.vue::handleCustomDrawOk()`

当前逻辑：

- 后端只校验 `close_time`，封盘后就允许自定义开奖号码并立即写 `result`、`status = 3`、调用结算。
- 前端也只用 `isBeforeCloseTime()` 禁用自定义开奖按钮。

- 未到开奖时间可以选择方案，但不允许立即开奖结算。
- 后台开奖时间和前端用户开奖核对时间必须一致，例如都是 8:33。

因此必须调整：

## 十三、客户补充确认

客户后续已补充确认以下细节：

1. 选定开奖计划后，在正式开奖时间前允许总管理员改选或撤销。

   当前代码是不允许重复提交手动计划。开发时要增加改选/撤销能力、权限控制、操作日志，并保存每次改选前后的号码、目标杀率、实际杀率、预计利润和预计派彩。只要还没到正式开奖时间、还没公布和结算，总管理员都可以改；到开奖时间后不再允许改。

2. 只允许封盘后生成和选择方案。

   封盘前不显示方案，也不做预览；封盘后订单固定，系统再一次性生成本期可选方案，并允许总管理员锁定。

   例如开奖时间为 8:33，如果 8:33 仍没有总管理员选择方案，并且本期有投注，系统不随机开奖、不自动结算。用户侧继续显示“等待开奖”，后台显示告警“本期未选择开奖计划，已暂停自动结算”。

4. 负盈利方案、改选、撤销只允许总管理员操作。

   普通管理员最多只能查看方案；总管理员选择负盈利、改选或撤销时必须二次确认并记录操作日志。

5. 通杀 100% 展示在同一列表。

   展示方式示例：本期订单可杀 10%、28%、30%、70%、100%，后台在同一个列表里自行选择。100% 仍建议加醒目标识和二次确认，避免误点。

6. 无投注期次自动开奖。

   如果封盘后本期没有任何投注，到开奖时间由系统自动随机开奖，不需要总管理员手动选择。因为没有投注就没有派彩风险，也没有杀率控制意义。

7. 期号自动延续。

   如果今天开到 180 期，后续后台没有人工操作，只要定时任务正常运行，系统应自动完成无投注期次开奖，并创建 181 期、182 期等后续期号。当前代码已有 `LotteryIssueService::getOrCreateCurrentIssue()` 创建下一期能力，但需要接入定时任务，才能保证无人操作也自动延续。

这说明最佳计划已有“覆盖所有主要玩法”的基础，但仍要补以下硬性防漏。

### 3. 必须补的玩法防漏点

1. 预计派彩和实际结算必须共用同一判奖口径

   当前有三处会计算中奖结果：

   - `OptimizedBestPlanService::calculateCombinedProfit()`：生成推荐方案时计算预计派彩。
   - `BestPlanLogic::executeDrawing()` 内部 `checkWin()`：选择方案后回显预计派彩。
   - `LotteryBetLogic::checkWin()`：真正开奖结算。

   开发时必须统一成同一套判奖服务，建议所有预计值也调用 `LotteryBetLogic::checkWin()` 或统一抽到 `LotteryPlayRuleService`。不能让三个地方各算一套，否则某个玩法改了规则，最佳计划仍会漏。

2. `正码/平码` 需要拆开计算

   当前 `OptimizedBestPlanService` 的 `KEYWORDS_NORMAL_NUMBER` 同时包含 `正码` 和 `平码`，计算时统一用 7 个号码判断。实际结算代码里：

   - `正码` 按前 6 个正码判断。
   - `平码` 按全部 7 个号码判断。

   因此开发时必须把 `正码` 和 `平码` 分开：

   - `正码` 只看 `m1_m6`。
   - `平码` 看 `m1_m6 + m7`。

   否则如果用户买了正码号码，而这个号码只出现在第 7 个特码里，最佳计划可能误算为中奖，导致预计派彩和实际结算不一致。

3. `executeDrawing()` 的预计值不能继续用独立 `checkWin()`

   `executeDrawing()` 现在会在锁定 `planned_result` 后回传 `win_count`、`total_payout`、`platform_profit` 等预计值，但它使用的是 `BestPlanLogic` 自己的 `checkWin()`。这个方法虽然已经接入部分扩展玩法，但仍可能和 `LotteryBetLogic::checkWin()` 不一致。

   建议改成：锁定方案时，后端用同一套结算模拟器重新计算预计派彩，返回字段命名为 `expected_payout`、`expected_profit`、`expected_profit_rate`，不要叫实际中奖/实际派彩。

4. `六肖/liuxiao` 规则必须按线上最终口径校准

   当前本地库中玩法名是 `六肖`，code 是 `liuxiao`，赔率为 `1.90`；代码里的 `LotteryPlayRuleService::getSixSpecialZodiacRule()` 会把 `liuxiao` 当成 `6肖中特` 特殊规则处理，即只按第 7 个特码生肖判断，49 和局退本金。

   这里必须在开发前以线上当前玩法规则为准确认一次：

   - 如果线上 `liuxiao` 就是 `6肖中特`，最佳计划和结算都按特码判断。
   - 如果线上仍是旧 `六肖`，就不能用 `6肖中特` 规则覆盖。

   不确认会导致最佳计划预计派彩和实际结算产生偏差。

5. `一肖/yixiao` 如果启用，必须补规则

   当前本地库未启用 `一肖`，但迁移脚本里曾插入过 `一肖/yixiao`。如果其他环境存在并启用，当前最佳计划和结算都不能假设它不存在。开发时要增加启动自检：

   - 查出所有启用玩法 code。
   - 对每个 code 检查是否有判奖规则。
   - 没规则时后台提示“玩法未纳入最佳计划”，并阻止生成推荐方案。

### 5. 新增验收要求

1. 新增一个玩法覆盖测试脚本，读取 `la_play_method` 当前启用玩法。
2. 每个玩法自动构造一组命中和未命中订单。
3. 对同一期开奖结果同时跑：
   - `OptimizedBestPlanService` 预计派彩。
   - 锁定方案接口预计派彩。
   - `LotteryBetLogic::settleBetting()` 实际结算。
4. 三边金额必须一致。
5. 如果有玩法没有规则，测试直接失败。
6. 如果 `la_play_method` 新增启用玩法但测试矩阵没有覆盖，测试直接失败。
