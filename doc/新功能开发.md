# 新功能开发方案

更新时间：2026-07-04

## 一、客户已确认的业务规则

本轮客户回复后，需求边界调整为：

1. “删除按钮”不是撤单。
   - 删除用于后台清理历史下单数据。
   - 例如搜索 7 月 3 日订单后，可以单选或多选下注订单并删除。
   - 删除的是后台历史列表中的历史数据，不代表给用户退款，也不代表撤销下注。

2. “撤单”需要新增为独立功能。
   - 用于下注错误时撤销注单。
   - 只允许封盘前撤单。
   - 撤单需要走账务回滚：退余额、扣冻结、写流水、改注单状态、写操作日志。

3. 后台撤单也应遵守封盘前规则。
   - 已封盘后不允许撤单。
   - 已开奖、已结算订单不走撤单。

4. 已开奖、已结算订单仍然需要支持后台历史删除。
   - 后台历史下单列表需要删除按钮。
   - 后台历史记录里面也需要删除按钮。
   - 支持单选删除和多选批量删除。
   - 可删除昨日或更早历史数据。

5. “历史记录”指期号历史/开奖记录相关后台数据。
   - 例如 7 月 3 日订单开出的号码为 1,2,3,4,5,6,7。
   - 管理员今天核对完账单后，可以把这期开奖/期号相关后台历史数据删除。
   - 删除后后台不再保留这部分历史展示数据。
   - 但不能影响前台数据。

6. “6中1”不是“6肖中特/六肖”。
   - 玩法含义：49 个号码中任选 6 个号码下注。
   - 开奖的 7 个号码中，只要任意 1 个号码命中下注的 6 个号码之一，即为中奖。
   - 这是数字玩法，不是生肖玩法。

7. “6中1”无打和。
   - 不存在 49 和局、退本金之类逻辑。
   - 49 只是普通可选号码之一。
   - 选中 49 且开奖号中有 49，则按命中中奖处理。

## 二、核心设计原则

本功能必须拆成两套逻辑：

```text
后台历史删除 = 后台列表清理/隐藏历史数据，不回滚账务，不改变用户余额。
封盘前撤单 = 真正取消下注，必须回滚账务，并保留审计记录。
```

不能再把“删除”默认理解成“撤单”。

另外，客户要求“删除后台数据，但不影响前台数据”。因此实现时不能直接物理删除前台仍依赖的核心业务数据，例如用户注单、用户流水、开奖结果、期号结算结果等共享数据。推荐使用“后台可见性删除”：

```text
后台列表过滤已删除记录
前台接口继续按原数据读取
账务、结算、用户投注记录不受影响
```

如果某些表只服务后台分析缓存，且前台完全不读取，才可以考虑物理删除。

## 四、功能一：后台历史下单删除

### 1. 功能目标

后台历史下单列表增加删除能力：

- 单条删除。
- 多选批量删除。
- 支持按日期、期号、状态、用户等条件搜索后批量删除。
- 支持删除昨日或更早历史下单数据。
- 已开奖、已结算订单也允许后台删除历史展示数据。
- 删除不等于撤单，不退钱，不改用户余额，不回滚派奖。
- 删除后后台历史下单列表和后台统计不再显示这些记录。
- 前台用户投注记录、账务流水、开奖结果不受影响。

### 2. 推荐实现方式

不要直接物理删除 `la_betting_record`，因为该表是用户注单核心表，前台投注记录、账务、结算、统计都可能依赖它。

推荐给投注记录增加后台删除字段：

```sql
ALTER TABLE la_betting_record
  ADD COLUMN admin_deleted_at INT UNSIGNED NULL DEFAULT NULL COMMENT '后台删除时间',
  ADD COLUMN admin_deleted_by INT UNSIGNED NULL DEFAULT NULL COMMENT '后台删除管理员ID',
  ADD KEY idx_admin_deleted_at (admin_deleted_at);
```

后台历史下单查询默认增加：

```text
admin_deleted_at IS NULL
```

前台投注记录查询不加这个条件，确保前台不受影响。

### 3. 接口建议

新增后台接口：

```text
POST /adminapi/best_plan/deleteBetRecords
```

参数：

```text
ids: number[]
```

权限：

```text
只允许总管理或有历史下单删除权限的后台账号
```

处理逻辑：

1. 校验 `ids` 不为空。
2. 查询这些注单是否存在。
3. 只更新后台删除字段，不改注单状态。
4. 不更新用户余额。
5. 不更新冻结金额。
6. 不更新中奖记录。
7. 不更新账户流水。
8. 写入后台操作日志，记录管理员、删除数量、注单 ID、筛选条件或日期范围。
9. 返回删除数量。

### 4. 前端页面

修改：

- `vue/admin/apps/web-antd/src/views/control-panel/order-history/index.vue`
- `vue/admin/apps/web-antd/src/api/best-plan.ts`

页面新增：

- 表格勾选框。
- 单行删除按钮。
- 批量删除按钮。
- 二次确认弹窗。

确认文案建议：

```text

```

## 五、功能二：后台历史记录/期号历史删除

### 1. 功能目标

后台历史记录增加删除能力：

- 单条删除。
- 多选批量删除。
- 可删除昨日或历史期号数据。
- 适合核对完账单后清理后台历史展示。
- 不影响前台开奖数据和用户投注数据。

### 2. 表设计建议

`la_best_plan_history` 是后台分析历史，优先支持后台删除字段：

```sql
ALTER TABLE la_best_plan_history
  ADD COLUMN admin_deleted_at INT UNSIGNED NULL DEFAULT NULL COMMENT '后台删除时间',
  ADD COLUMN admin_deleted_by INT UNSIGNED NULL DEFAULT NULL COMMENT '后台删除管理员ID',
```

```text
admin_deleted_at IS NULL
```

```sql
ALTER TABLE la_lottery_issue
```

```text
admin_hidden_at IS NULL
```

前台开奖历史接口不使用该过滤条件。

### 3. 接口建议

后台分析历史删除：

```text
POST /adminapi/best_plan/deleteHistories
```

参数：

```text
ids: number[]
```

```text

```

```text

```

处理逻辑：

1. 校验权限。
2. 批量标记后台删除/隐藏。
3. 不删除用户注单。
4. 不删除前台开奖结果。
5. 不回滚结算。
6. 写入后台操作日志。
7. 返回删除/隐藏数量。

### 4. 需要开发时核对

开发前需要看当前“历史记录”页面实际读取的是：

```text

```

还是某个期号列表接口。

如果只读 `la_best_plan_history`，第一版只做 `deleteHistories` 即可。

如果页面还需要删除期号历史，则补 `deleteIssueHistories`，但必须走后台隐藏，不物理删共享期号数据。

## 六、功能三：封盘前撤单

### 1. 功能目标

新增真正撤单能力，用于下注错误时取消下注：

- 前台用户可撤自己的注单。
- 后台管理员可帮用户撤单。
- 只允许封盘前撤单。
- 已封盘不允许撤单。
- 已开奖、已结算不允许撤单。
- 撤单要退还下注金额并更新账务。
- 撤单保留审计记录，不能物理删除。

### 2. 可撤单条件

推荐统一校验：

```text
la_betting_record.status = 0
la_betting_record.is_settled = 0
当前时间 < 对应期号封盘时间
```

如果当前代码只有开奖时间或封盘配置，需要按现有封盘逻辑取值，不能只用前端时间判断。

### 3. 账务回滚

下注时系统会：

```text
扣减用户余额
增加冻结金额
增加用户累计投注额 total_bet
写入投注记录
写入账户流水
增加期号 total_bet_amount
```

撤单时必须在事务内回滚：

```text
用户余额 + 投注金额
用户冻结金额 - 投注金额
用户累计投注额 - 投注金额
期号 total_bet_amount - 投注金额
注单状态改为 3 = 已撤单
写入撤单退款流水
写入后台/用户操作日志
```

### 4. 后端服务建议

新增公共服务，供后台和前台共用：

```text
server/app/common/service/BetCancelService.php
```

方法建议：

```text
cancelBeforeClose(int $betId, int $operatorId, string $operatorType, int $userId = 0)
```

职责：

1. 开启事务。
2. 查询并锁定注单。
3. 校验注单存在。
4. 校验用户归属。
5. 校验未开奖、未结算。
6. 校验未封盘。
7. 查询并锁定用户账户。
8. 回滚余额、冻结金额、累计投注额。
9. 回滚期号投注总额。
10. 更新注单状态为已撤单。
11. 写账户流水。
12. 写操作日志。
13. 提交事务。

### 5. 前台撤单接口

新增接口：

```text
POST /api/lottery_bet/cancelBet
```

权限：

```text
只能撤当前登录用户自己的注单
```

前端修改：

- `vue/home/src/services/api.js`

按钮显示规则：

```text

其他状态：不显示或禁用
```

确认文案：

```text

```

### 6. 后台撤单接口

新增接口：

```text
POST /adminapi/best_plan/cancelBetBeforeClose
```

参数：

```text
id: number
```

权限：

```text
只允许总管理或有撤单权限的后台账号
```

后台历史下单页面可在未封盘注单上显示“撤单”按钮。注意该按钮要和“删除”分开：

```text

撤单 = 封盘前取消下注并退款
```

## 七、功能四：6中1数字玩法

### 1. 玩法定义

客户确认后的规则：

```text
从 1-49 中任选 6 个号码下注。
开奖有 7 个号码。
只要开奖 7 个号码中的任意一个，命中下注 6 个号码中的任意一个，即中奖。
没有打和。
```

示例：

```text
下注：03, 08, 12, 18, 27, 49
开奖：01, 02, 09, 18, 31, 44, 47
结果：中奖，因为 18 命中
```

示例：

```text
下注：03, 08, 12, 18, 27, 49
开奖：01, 02, 09, 19, 31, 44, 47
结果：未中奖
```

示例：

```text
下注：03, 08, 12, 18, 27, 49
开奖：01, 02, 09, 19, 31, 44, 49
结果：中奖，因为 49 命中。没有和局。
```

### 2. 和现有六肖的区别

不能复用现有 `liuxiao / 六肖 / 6肖 / 6肖中特 / 六肖中特` 规则。

区别如下：

```text
六肖：选生肖，通常按特码生肖判断。
6中1：选数字，按全部 7 个开奖号码判断。
```

### 3. 后端实现建议

在玩法规则服务中新增独立 code，例如：

```text
liuzhongyi
six_pick_one
```

不要映射到 `liuxiao`。

修改位置：

- `server/app/common/service/LotteryPlayRuleService.php`
- `server/app/api/logic/LotteryBetLogic.php`
- `server/app/adminapi/logic/BestPlanLogic.php`

规则判断：

```text
下注号码集合 bet_numbers，数量必须为 6
开奖号码集合 draw_numbers，数量为 7
如果 bet_numbers 与 draw_numbers 有交集，则中奖
否则未中奖
不处理和局
```

### 4. 前端实现建议

前台下单页：

- `vue/home/src/views/Betting.vue`

要求：

```text

必须选择 6 个号码
提交时按数字列表传给后端
```

前台投注记录：

- `vue/home/src/views/BetStatus.vue`

要求：

```text
显示玩法名 6中1
显示所选 6 个号码
中奖结果按后端判定展示
```

后台历史下单：

- `vue/admin/apps/web-antd/src/views/control-panel/order-history/index.vue`

要求：

```text

```

## 十一、当前仍需开发时现场确认的小点

客户大的业务方向已经明确，可以进入开发。开发前只需要在代码层面确认两个实现细节：

1. 后台“历史记录”页面最终要删的是 `la_best_plan_history`，还是还要同时支持隐藏 `la_lottery_issue` 期号记录。

## 十二、给客户的大白话说明

这次会把“删除”和“撤单”分开做。

删除是后台清理历史数据，比如你搜 7 月 3 日的订单，可以单选或多选删除。删除后后台历史列表不显示，但不会退款、不会改用户余额，也不会影响前台用户数据。

撤单是下注错了以后取消下注，这个只允许封盘前操作。撤单会把下注金额退回用户余额，并且留下流水和操作记录。

6中1会按数字玩法做，不按生肖做。也就是 1 到 49 选 6 个号码，开奖 7 个号码里面只要中任意一个就中奖，没有和局。
