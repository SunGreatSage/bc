# 后台实时分析游戏优化方案

## 1. 现状概述
当前后台实时分析接口 `/adminapi/best_plan/calculateRealtime` 全量依赖 `app/common/service/OptimizedBestPlanService`。服务在每次请求中都会：
1. 读取本期全部下注记录，生成权重；
2. 针对 6 个特码候选、12 个正码池，枚举最多 120 组组合；
3. 对每组组合再次遍历全部下注，逐条模拟派彩并判定（含多肖、49 退还的逻辑）。

当投注笔数达到几百乃至上千时，组合数量 × 下注笔数 迅速升至百万级，PHP 请求极易超过 30s 超时限制。为了恢复后台实时分析的可用性，需要对「组合数量」「派彩计算」与「请求模式」做优化。下文分短期和中长期给出可落地的方案。

## 2. 性能瓶颈
- **组合数量固定**：`SPECIAL_CANDIDATE_LIMIT=6`、`NORMAL_POOL_LIMIT=12`、`MAX_COMBOS_PER_SPECIAL=120` 在大数据量下过于激进，导致 6 × 120 = 720 种组合，每种组合都要遍历全部下注。
- **派彩计算缺乏复用**：`calculateCombinedProfit()` 每次都会重新遍历 `$this->allBets`，即便多组组合之间大量重复，也没有做缓存。
- **同步阻塞**：接口是同步调用，且没有任何缓存层/任务队列，导致所有运算都卡在 HTTP 请求中。

## 3. 短期优化（当天即可上线）
1. **动态收缩候选**  
   - 根据下注总笔数/金额动态调整 3 个常量，例如：下注 < 200 保持默认；200~500 降为 4/10/40；>500 降为 3/8/20。  
   - 代码位置：`OptimizedBestPlanService::findBest7Numbers()` 进入主循环前，依据 `$this->getBetCount()` 动态重设常量或改为成员变量。
2. **拆分投注分类缓存**  
   - 先按照玩法把下注分组（特码、正码、特肖、多肖），计算好每种玩法对应的投注数组。  
   - 在 `calculateCombinedProfit()` 中只针对需要的玩法组遍历，且可以缓存“某个号码中奖时的总赔付”结果，避免重复遍历。
3. **控制请求超时时间**  
   - 在 `php.ini` / Nginx 中把 `max_execution_time`、`fastcgi_read_timeout` 暂时提升到 60s，防止正在处理的请求直接被掐断，为用户保底。该方法仅作为过渡，仍需配合前两项降低计算量。

## 4. 中期优化（1~3 天）
1. **异步计算 + 缓存**  
   - 把 `findBest7Numbers()` 改成命令行任务（可参考 `debug_realtime.php`），由定时器或手动按钮触发。计算结果写入缓存表（如 `la_best_plan_cache`），接口只读缓存，耗时降为毫秒级。
2. **增量更新**  
   - 在下注新增时把最新订单 append 到缓存，不必每次重头计算。可维护一个“本期投注 Hash”，只有投注有变化才触发重算。
3. **多进程/并发**  
   - 对于组合遍历，可使用 PCNTL/并行扩展或 Swoole Task，把不同特码的组合分配到多个 worker 中并行计算，提高 CPU 利用率。

## 5. 长期优化方向
1. **策略算法升级**  
   - 将“精确穷举”改为“启发式搜索/遗传算法/模拟退火”，只探索高价值组合，避免 O(组合 × 下注) 的全遍历。  
2. **服务拆分**  
   - 通过 Go/Node 等常驻服务承载计算模块，PHP 只负责下发任务与展示结果，可以充分利用多核性能。  
3. **前后台交互优化**  
   - 后台页面改为“提交计算任务 → 轮询结果”，避免管理员长时间等待 HTTP 响应。
